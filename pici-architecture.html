How Pici fits together.

A code-based map of the runtime boxes, the paths between them, and the places where growth is starting to hurt. Pici is best understood as a compact agent kernel surrounded by an increasingly capable product runtime: terminal UX, durable sessions, model adapters, Lua policy, and multi-agent coordination.

Executive read

The architecture has a good event-driven center. Most pressure is now at the product-runtime seams around that center, where composition, concurrency, persistence, and presentation meet.

The shortest useful model: front ends create an AgentSession; the session drives an Agent; the agent snapshots AgentState and runs AgentLoop; the loop streams through a provider, executes tools, and emits typed events; adapters consume those events for rendering, persistence, RPC/SSE, and coordination. Lua hooks can intercept context, tools, events, commands, and presentation along the way.

Strong seam

Typed event stream

Providers, the loop, renderers, persistence, RPC, and telemetry communicate through explicit message/event types. That gives Pici a clean place to observe behavior and add adapters.

Primary architecture debt

Composition lives in the CLI

cmd_run() in src/main.cpp owns setup, lifecycle, closures, REPL commands, UI, mailbox delivery, hooks, and task wiring. The reusable runtime exists only partially in AgentSession.

Primary scaling debt

Coarse serialization

ACP serializes durable runs process-wide. Session and mailbox stores hold broad mutexes around filesystem or SQLite work. These are safe first implementations but cap independent concurrency.

Important boundary: pi-core currently includes orchestration, tools, Lua, persistence, mailbox, and terminal rendering. pi-http adds curl-backed providers/auth. The library boundary is therefore a build/link boundary, not a strict domain boundary.

One turn, end to end

This is the dominant data path. Tools can cause multiple model messages within one turn, and steering/mailbox messages can enter at safe boundaries before the loop stops.

1 · InputCLI/RPC/ACP produces user message envelopes plus source/presentation metadata.
2 · SessionAgentSession::run_messages starts a stream and later journals completed messages.
3 · SnapshotAgent copies prompt, transcript, model, tools, identity, and loop callbacks.
4 · PrepareLua/context hooks transform and budget messages; provider conversion follows.
5 · ModelLLMClient builds HTTP payload, parses SSE, and emits incremental assistant events.
6 · ToolsCalls are validated, gated by hooks, then run sequentially or with std::async.
7 · EventsMessage/tool/turn events update state and fan out to renderer, RPC/SSE, Lua, tasks, and diagnostics.
8 · CommitMessage-end records flush to JSONL; optional compaction uses epoch-checked durable commit.
Control flow

Why the loop repeats

An assistant response containing tool calls is not terminal. Tool results are appended to context, queued steering is injected, and another model request begins. The loop stops on a normal assistant answer, a configured stop hook, cancellation/error, or after follow-up work has drained.

Threading model

Where work runs

Each agent run has a jthread. Provider streaming runs in that worker. Parallel tool calls use one std::async task per call. Subagents have their own runners. Mailbox maintenance and terminal title updates add background threads. UI-facing activity is queued back toward the presentation owner.

Coupling hotspot

cmd_run()

The source comments already acknowledge that renderer, session, mailbox, and REPL dispatch share one scope through closures. This makes a small CLI feature easy to add locally but hard to reuse in ACP or test without reproducing setup.

Concurrency hotspot

Tasks + mailbox

AgentTaskManager and MailboxCoordinator coordinate manager locks, per-task locks, runners, callbacks, leases, and shutdown. Their comments show careful lock-order work; that is also evidence that this subsystem needs explicit state-machine boundaries and stress testing.

Likely bottlenecks

Ranked by confidence and likely user impact. “Confirmed by code” means the scaling behavior is directly visible; it does not claim a production profile was run.

Streaming renderer work grows with transcript size

CPU · confirmed

Viewport repaint renders the growing Markdown buffer and splits physical lines on each text delta; diff Markdown repeatedly scans rendered output for cursor rows. Existing plans E/F/G explicitly describe O(N²)-like cumulative work and discarded allocations. Region rendering is also state/geometry heavy, though its exact profile needs measurement.Evidence: plan_E_split_lines_ring_buffer.md · plan_F_incremental_row_count_tracking.md · plan_G1–G4 · stream_renderer.cpp

ACP durable runs are globally serialized

Throughput · confirmed

Every run takes the single process-wide durable_run_mutex before creating/restoring an AgentSession; the lock is retained by streaming closures. Independent sessions therefore cannot run concurrently even though the HTTP server has a thread pool.Evidence: acp/handlers.cpp:40 and :580–587

Transcript copies and transformations are O(context) per turn

Memory/CPU · structural

AgentState::messages() returns a vector copy; context_snapshot() copies messages and tools; hooks and provider transforms may copy again. As sessions grow, every model round—including tool-induced rounds—pays more allocation and memory-bandwidth cost before network latency begins.Evidence: agent_state.h snapshots · agent.cpp create_context_snapshot · providers/transform_messages.cpp

Session operations scan files under one mutex

I/O · confirmed

Listing reads every session file to accumulate metadata; child detection scans the directory and headers; load recursively replays JSONL ancestry. These operations hold SessionStore::mutex_. Message completion also flushes each journal line synchronously. This is fine for dozens of sessions, less so for thousands or large histories.Evidence: session_store.cpp list(), has_children(), load(), write_line_locked()

Mailbox concurrency funnels through one store connection

Contention · structural

MailboxStore owns one SQLite handle and guards public operations with one mutex. MailboxCoordinator adds its own frequently acquired mutex around delivery state. WAL helps cross-process behavior, but in-process calls still serialize and long transactions/queries can block unrelated mailbox actions.Evidence: mailbox_store.h/.cpp · mailbox_coordinator.cpp lock sites

Parallel tools create an unbounded thread fan-out per response

Threads · potential

Parallel mode launches one std::async(std::launch::async) per tool call. Normal model outputs keep this small, but there is no executor/backpressure boundary. Combined with subagent runners and multiple sessions, bursts can oversubscribe CPU and complicate completion-order presentation.Evidence: agent_loop.cpp around parallel tool execution · plans/parallel-tool-call-live-ordering.md

One Lua hook instance serializes calls through its VM lock

Extension latency · potential

Lua state cannot be entered concurrently, so hook/tool operations guard VM access. Slow policy or formatting hooks sit on request, tool, and rendering paths. Separate subagent hook instances reduce global contention, but any one session can still be delayed by synchronous add-on work.Evidence: lua_tool.cpp mutex-guarded hook invocations

Where to focus next

The best order is to measure first, remove known user-facing cliffs second, then reshape ownership so later work does not multiply across CLI/RPC/ACP.

Now · establish truth

Benchmarks & service-level signals

  1. Add deterministic benchmarks for 10k/100k streamed tokens across each renderer.
  2. Measure context snapshot/transform bytes and duration per model round.
  3. Load-test ACP with independent session IDs and mailbox/task churn.
  4. Expose queue, lock-wait, SQLite, render-frame and provider timing metrics through existing diagnostics/OTel.
Next · remove cliffs

Fix confirmed bottlenecks

  1. Execute renderer plans E/F/G or simplify to region + raw as the removal plan proposes.
  2. Replace ACP’s global mutex with keyed per-session execution ownership; allow unrelated sessions concurrently.
  3. Add bounded tool execution rather than one new thread per call.
  4. Move session listing metadata to an index/cache and shorten lock-held I/O.
Then · reduce coupling

Promote a shared runtime

  1. Grow AgentSession into a SessionRuntime that owns model/auth/tools/hooks/tasks/mailbox policies.
  2. Extract CLI command dispatch and UI ownership from cmd_run().
  3. Make CLI, JSONL RPC, and ACP thin adapters over the same construction path.
  4. Split pi-core presentation and product services from the kernel when ownership is clear.
Later · scale the model

Context & coordination

  1. Introduce shared/immutable transcript snapshots or copy-on-write history.
  2. Add provider-independent local compaction/trimming fallback.
  3. Give task/mailbox lifecycle explicit transition objects and adversarial concurrency tests.
  4. Consolidate provider parser/request utilities without erasing genuine protocol differences.
Highest ROI refactor

Shared runtime construction

This prevents behavioral drift across the three entry surfaces and creates one home for session lifecycle, hooks, tools, task limits, mailbox identity, auth, diagnostics, and persistence. Do it after adding characterization tests and measurements, because cmd_run() currently encodes many subtle terminal and mailbox invariants.

Avoid premature work

Do not optimize provider network latency in C++ first

Model calls dominate wall time, but much of that is external. The controllable pain is pre-request copying, token-by-token rendering, coarse serialization, and synchronous persistence. Measure request construction and parser CPU, then optimize only if it is material.

Design notes worth preserving

Several current choices are good foundations. Refactors should keep their guarantees explicit.

Typed messages and events are the architectural spine

Message, AgentEvent, and EventStream decouple provider streaming from renderers and wire adapters. Continue adding typed events at real commit points—such as the existing mailbox reply notice—rather than inferring truth from tool names or formatted text.

Idle-only transitions protect cross-cutting state

Model switches, session restores, and compaction commits are guarded against active streaming, pending tools, and queued steering/follow-ups. The compaction transcript epoch prevents a slow network replacement from overwriting newer messages. Preserve this transactional shape in a shared runtime.

Append-only persistence favors recovery and debuggability

JSONL messages, metadata, truncation, and compaction replacement records are easy to inspect and replay. An index can accelerate discovery without abandoning the journal as the source of truth.

Lua is policy and customization; native code owns hard mechanisms

The current split works best when C++ owns sandboxing, durable delivery, task lifecycle, and typed events while Lua chooses presentation and higher-level policy. Avoid forcing security-critical command parsing or concurrency ownership entirely into add-ons.

Tests are a real asset

The tree contains about 22.9k lines of C++ tests across 39 source files plus Lua add-on tests. Agent loop, readline, Lua, region renderer, compaction, terminal, providers, mailbox, tasks, RPC and ACP all have dedicated coverage. Use those suites as characterization protection during extraction.
