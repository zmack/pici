Postmortem and follow-up plan

Making pi-cpp work with the local OpenAI-compatible API

The target API was http://127.0.0.1:8080/v1, serving Qwen3.6-35B-A3B-UD-IQ4_NL.gguf through a llama.cpp-style server.

What was broken

The project assumed a different OpenAI-compatible server profile.

The CLI defaulted to Ollama-style settings and the provider emitted OpenAI-specific fields that the local llama.cpp endpoint did not want. Even when the endpoint was reachable, the CLI either produced no text or crashed before the integration was usable.

Wrong defaults

chat pointed at localhost:11434 and model llama3.2, not the local 8080 server.

Wrong payload shape

The provider always sent OpenAI-specific fields such as store, stream_options, and max_completion_tokens.

What we observed

The visible behavior hid several independent failures.

Symptom What it meant Status
Build failed in core files Existing stray commas in std::ranges calls blocked any verification. Fixed
HTTP target failed to compile curl/easy.h was included before public curl definitions. Fixed
CLI produced empty output The provider was not registered reliably, and Qwen streamed reasoning-only chunks by default. Fixed
CLI waited, then printed everything at once Agent::prompt() discarded a std::async future, whose destructor blocked until the request completed. Fixed
CLI segfaulted libcurl callbacks were passed through varargs without explicit function-pointer conversion. Fixed

Root causes

Compatibility was implicit instead of tested as a provider contract.

Provider compatibility drift

OpenAI-compatible APIs differ in small but important ways. The local llama.cpp server wanted max_tokens, no usage stream options, and Qwen thinking disabled.

Static registration risk

The CLI linked pi-http, but without an explicit symbol reference the provider registration path could be skipped.

Low-signal errors

Streaming errors and non-SSE responses could collapse into an empty assistant message instead of an actionable CLI error.

Async boundary blocked

std::async looked asynchronous, but the discarded future forced the caller to wait for completion before consuming events.

Insufficient build hygiene

Compile blockers and a curl varargs bug were only found after trying to exercise the integration end to end.

What changed

We made the local API a first-class compatibility profile.

1. Discover Queried /v1/models and found the served Qwen model.
2. Default Pointed CLI defaults at 127.0.0.1:8080/v1.
3. Normalize Added local llama.cpp compatibility detection and payload shaping.
4. Stabilize Fixed provider registration, curl callback safety, async stream forwarding, and visible errors.
5. Verify Added focused provider tests and ran the full CTest suite. 
./build/pi-cli chat

# Defaults:
#   base-url: http://127.0.0.1:8080/v1
#   provider: llamacpp
#   model:    Qwen3.6-35B-A3B-UD-IQ4_NL.gguf

Payload contract

The local request now avoids OpenAI-only assumptions.

Field OpenAI default Local llama.cpp behavior
stream true true, with SSE lines parsed as curl receives them
max_completion_tokens used replaced by max_tokens
stream_options.include_usage used omitted
chat_template_kwargs.enable_thinking not needed set to false

Verification

The integration was checked at three levels.

Provider unit coverage

test-openai_completions asserts the local payload shape.

Full test suite

ctest --test-dir build --output-on-failure passes all seven tests.

Local smoke test

The CLI successfully returns OK from the local server.

printf 'Say OK.\n/quit\n' \
  | timeout 20s ./build/pi-cli chat \
      --system 'Answer with one short final sentence.'

Going forward

Keep provider differences explicit, tested, and visible.

  • Add a compatibility test whenever a provider-specific flag is introduced or removed.
  • Keep CLI defaults aligned with the documented local development server.
  • Run cmake --build build, ctest, format, and tidy before publishing integration changes.
  • Prefer explicit registration calls over relying only on static initialization across libraries.
  • Surface provider and HTTP errors in CLI output instead of allowing empty assistant messages.
  • For curl callbacks, use named callbacks or explicit function-pointer conversion before passing them through varargs.

The durable fix is not just the llama.cpp profile. It is treating every OpenAI-compatible backend as a versioned contract with tests.
