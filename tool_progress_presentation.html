Tool progress & mutation safety

Live bash output, immediate tool-start events, full-output preservation, and serialized file writes. One-day build that turns a blind TUI into a live one.

Where we are

7 builtins: read, bash, edit, write, grep, find, ls. Workspace-confined, fuzzy edits, gitignore-aware. Solid — but no live progress.

What pi has

Bounded streaming accumulation, live update callbacks firing during execution, full-output temp files, file-mutation queue, immediate tool-start events.

Goal of this deck

Explain exactly what to change in builtin_tools.cpp, agent_loop.cpp, and stream_renderer.h to close the gap — with minimal risk.

Context: Phase 1 (lifecycle hardening) + Phase 2 (AgentSession) are done. This is the recommended small win before Phase 3 durable context.

02 — why it matters

The agent goes dark for 30 seconds while bash compiles

Today's UX: model calls bash("make test") and the viewport shows only the tool args. No output until the process exits. Three parallel tools show nothing until all finish. Large output is silently truncated. Two edits to the same file can race.

⏳ No live bash

pipe → poll → accumulate → return one blob at end. 64KB kMaxBytes buffer. User stares at static screen.

UX: bad

👻 Late start events

In parallel mode, on_tool_start emitted after futures join. 3 tools * 10s = 10s of silence then 3 pops.

UX: bad

✂️ Truncation loss

Over 64KB → "[Truncated]" suffix. No temp file, no full log path. Important build errors disappear.

info loss

⚠️ Write/write race

edit + edit on same file can both read_text_file then race write_text_file. Last write wins partially.

correctness
If a tool takes >500ms, the user should see it started immediately and see progress streaming.

03 — current implementation

BashTool is a careful fork+poll — but it doesn't stream

Location: src/core/builtin_tools.cpp:712-925. Forks sh -c "cd $cwd && $cmd" in new process group, non-blocking pipe, self-pipe wakeup for stop_token, timeout kills tree, drains remainder, returns single TextToolResult.

  • New pgid so kill(-pid) kills child tree
  • Self-pipe to unblock poll on abort
  • Timeout kills with TERM → 200ms → KILL
  • Drain loop after exit to capture last bytes

The missed opportunity

Poll loop already sees data chunk by chunk (buf[4096]). It appends to output but never forwards that partial buffer to UI. 2 extra lines would fix it.

// current poll — accumulates only
string output; reserve 4096
char buf[4096]

while (true) {
  if (now >= deadline) { kill_tree(); timed_out=true; break; }
  poll(fds={pipe, wakeup}, remaining)

  if (wakeup POLLIN) { kill_tree(); aborted=true; break; }
  if (pipe POLLIN) {
    nr = read(pipe, buf)
    output.append(buf, nr)
    if (output.size() >= kMaxBytes) break
    // ← should call on_update here
  }
}
close + waitpid
return TextToolResult(truncate_head(output))

04 — wiring that exists but is unused

The plumbing is there — BashTool just never calls it

Every ToolDefinition::execute receives ToolUpdateCallback on_update. The agent loop wraps it to emit ToolExecutionUpdateEvent. But BashTool::execute ignores the param. So live updates are dead code today.

Message types — already exists 
// src/core/message_types.h
using ToolUpdateCallback =
  function<void(shared_ptr<ToolResult>)>;

class ToolDefinition {
  virtual shared_ptr<ToolResult> execute(
    string_view call_id,
    string_view args_json,
    stop_token,
    ToolUpdateCallback on_update = {}) const = 0;
};
Agent loop — already wired 
// src/core/agent_loop.cpp:329
ToolExecutionOutcome execute_tool_safely(
  const PreparedToolCall &call,
  emit, stop_tok) {
  return call.tool->execute(
    call.tool_call.id,
    call.args_json,
    stop_tok,
    [emit, call](auto partial){
      emit(ToolExecutionUpdateEvent(
        call.tool_call.id,
        call.tool_call.name,
        call.args_json,
        partial->content(),
        location()));
    });
}
Fix for BashTool — ~10 LOC

On each successful read from pipe, after accumulating, call on_update(TextToolResult(output_so_far)). Throttle to e.g. every 100ms or 1KB to avoid flooding renderer. Check on_update is not null before calling — Lua tools may not pass it.

if (on_update) {
  auto now = steady_clock::now();
  if (now - last_emit > 100ms ||
      output.size() - last_emit_size > 1024) {
    on_update(make_shared<TextToolResult>(output));
    last_emit = now;
    last_emit_size = output.size();
  }
}
Renderer side — new hook

Today Renderer has on_tool_start and on_tool_end. We need progressive:

// stream_renderer.h
virtual void on_tool_update(
  string_view call_id,
  string_view tool_name,
  string_view partial_content) {}

Default no-op, backward compatible. RawRenderer ignores. DiffMarkdownRenderer could show as expanding block. ViewportRenderer shows as scrollable live output. AcpSseRenderer re-emits message.part.

Throttle in tool, not in renderer. Tool knows byte rate; renderer should be dumb and fast.

05 — tool start timing

Parallel tools: start must fire before async launch, not after

In execute_tool_calls_parallel (agent_loop.cpp: ~680), intention was source-ordered events for deterministic rendering. So it spawns all futures, waits, then emits ToolExecutionStart + result in order.

Today — late events
for tc in tool_calls:
  prepare
  spawn async { execute; finalize }

join all futures

for finalized in source_order:
  emit Start(id, name, args)   // 10s late
  emit MessageStart
  emit MessageEnd
  emit End(id, result)

Result: viewport shows nothing while 3×10s tools run. Then 3 blocks appear instantly. Model already asked for other tools that whole time? No feedback.

Proposed — immediate start
for tc in tool_calls:
  emit Start(id, name, args)   // NOW — visible in <1ms
  prepare
  spawn async { execute; finalize }

join all futures

for finalized in source_order:
  // Start already emitted, only emit result
  emit MessageStart(result)
  emit MessageEnd(result)
  emit End(id, result)

This keeps result ordering deterministic (ends in source order) but gives immediate feedback. Sequential path unchanged — it already emits start before execute.

To think about

Should we also add ToolExecutionUpdateEvent emission between start and end? Yes — carried by execute_tool_safely wrapper, no change needed in parallel harness itself. Start early + updates mid-flight = live UI.

06 — mutation safety

Two edits to the same file should never race

Agent loop's execute_tool_calls_parallel launches all tools whose execution_mode() == parallel concurrently. All builtins currently return parallel (default in ToolDefinition). So edit(A) + edit(B) both read_text_file → apply_edits → write_text_file at same wall time.

Race scenario 
User: "fix both bugs in foo.cpp"
Model calls:
  edit(path="foo.cpp",
    oldText="funcA old", newText="funcA new")
  edit(path="foo.cpp",
    oldText="funcB old", newText="funcB new")

Timeline parallel:
T0  T1 read foo.cpp (same content)
T1  T1 apply_edits in RAM (different)
T2  T1 writes → contains fix A only
T2  T2 writes → contains fix B only
                     ↑ fix A lost, or partial write

Result: corrupted file or missing one fix.
No file lock, no mtime check, no queue.
Three levels of fix (escalating) 
// L1 — minimal, correct, 2 lines (RECOMMENDED FOR NOW)
ToolExecutionMode WriteTool::execution_mode() const {
  return ToolExecutionMode::sequential;
}
ToolExecutionMode EditTool::execution_mode() const {
  return ToolExecutionMode::sequential;
}
// Loop already has has_sequential → sequential path

// L2 — per-path mutex
static shared_mutex file_mutexes[shards];
lock = file_mutexes[hash(path)]

read + apply + write under lock
prevents cross-batch races too

// L3 — FileMutationQueue (pi's approach)
queue{path, content, mtime}
single writer thread, dedupes, mtime checks,
writes coalesced. Overkill for now.

Why L1 is enough today

agent_loop.cpp: execute_tool_calls already checks has_sequential && — if any tool in batch is sequential, whole batch runs sequentially. So marking write/edit sequential serializes them within a batch and guarantees no intra-batch race.

What L1 does NOT fix

Across batches (turn 1 edit + turn 2 edit overlap due to abort/retry, or Lua tools). For that, L2 per-path mutex is ~60 LOC and true fix. L3 queue is ~200 LOC, only if we want pi-parity.

07 — output loss

Truncation without preservation loses the most useful bits

kMaxBytes = 64KB guards model context size. But current truncate_head drops tail and adds note:

[Truncated: showing 2000 of 8500 lines]
or
[Truncated: 884 lines shown (64KB limit)]

No temp file. No way for agent or user to recover full output. If build error is at line 8200, it is gone. Agent retries blindly, wasting tokens.

Current
  • read: truncates at 64KB + 2000 lines
  • bash: truncates at 64KB after exit
  • grep/find/ls: truncates at limit + 64KB
  • details() always nullopt
Proposed: preserve + point
// builtin_tools.cpp helpers
path write_full_output(
  string_view tool_name,
  string_view call_id,
  string_view full_content) {
  auto dir = tmp_dir() / "pici" / "tool-outputs";
  create_directories(dir);
  auto p = dir / (tool_name + "-" + call_id + ".log");
  write_text_file(p, full_content);
  return p;
}

shared_ptr<ToolResult> result =
  make_shared<TextToolResult>(
    truncated_preview,     // content — goes to model
    false,
    full_path.string()     // details — shown to user
  );

Model sees 64KB preview (budget safe). Human sees "Full output at /tmp/pici/tool-outputs/bash-abc123.log" via renderer's details row. Same pattern pi uses: bounded accumulation + full path.

Renderer tweak

VerboseRenderer::on_tool_end already prints result.content() in gray. If result.details() present, print second line full output: /tmp/... in dim color. ACP renderer can include details as artifact part.

L2: + per-path mutex │ └─► returns ToolResult { content=preview (64KB), details=full_path?, is_error } Renderer ├─ Raw : ignores update, prints final only ├─ Diff/Viewport : on_tool_start: show "▶ bash ..." + spinner │ on_tool_update: replace partial in-place, scroll │ on_tool_end : final + dim details path └─ AcpSseRenderer : re-emits as message.part (live SSE)

Touches only 3 files

builtin_tools.cpp (bash streaming + full-output file + seq mode), agent_loop.cpp (start timing), stream_renderer.h/cpp (new on_tool_update virtual) + renderers.

Backward compatible

on_tool_update default no-op. Lua tools unaffected. Existing tests pass: they only assert final content, not event ordering (need adjustment for new start timing).

Sets up Phase 3

Once live updates work, durable mutation entries become easier: we already have the event stream point where to persist partials if we ever want crash-safe history.

09 — implementation plan

Four subtasks, ~130 LOC, one day

3a — Bash live streaming Wire on_update in BashTool poll loop. Throttle 100ms / 1KB. Thread-safe because emit is already mutex-protected in EventStream. ~25 LOC in builtin_tools.cpp
high impact
3c — Immediate tool start Move ToolExecutionStartEvent before async spawn in execute_tool_calls_parallel. Keep End emission in source order. Adjust 2-3 tests that assert event ordering. ~15 LOC
high impact
3b — Full-output path Add write_full_output() helper. In every builtin that calls truncate_head, if truncated, write full to temp and return TextToolResult(preview, details=path). Update renderers to show details. ~50 LOC
med impact
3d — File mutation safety L1: override execution_mode() → sequential for Write/Edit. L2 (optional same PR): per-path shared_mutex shards. ~10 LOC L1, ~60 LOC L2
quick win
Order
  1. stream_renderer.h: add on_tool_update + on_tool_details plumbing, update dispatch_event for new ToolExecutionUpdateEvent.
  2. agent_loop.cpp: move Start emit before spawn in parallel path. Verify sequential path already correct.
  3. builtin_tools.cpp: L1 sequential override for write/edit. Add full-output helper + wire details.
  4. builtin_tools.cpp: bash live on_update throttling.
  5. Renderers: Viewport shows update as expanding block, Raw ignores, Verbose prints dim details.
Risks & mitigations
  • Update flooding → throttle in tool (100ms) not global debounce
  • Event order test breakage → update test_agent_loop.cpp expectations: start before end but results still ordered
  • Large live buffer in renderer → cap rendered live output at 20KB tail, full only at end
  • Temp file leak → write under /tmp/pici/tool-outputs/ + mention in docs, or clean on session start for files >7d
  • Lua tools → they already receive on_update via lua_tool.cpp shim? Verify; if not, pass through there too
