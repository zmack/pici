Code review summary

Antipatterns found in this project so far

These were not just style issues. Most were correctness risks: dangling references, tests that could not link cleanly, optional code paths that decayed, and APIs that invited misuse.

Risk category

Async lifetime, stream semantics, build configuration, state safety, serialization, and HTTP resource handling.

Main theme

Several APIs worked only if every caller remembered hidden rules. That is brittle engineering.

Fix direction

Make ownership explicit, make final states automatic, build all test programs correctly, and keep optional code honest.

Antipattern 1

Capturing returned objects by reference in async work

The agent returned an EventStream while background tasks captured that same stream by reference. Once the function returned, the producer could be writing through a dangling reference.

Why it is bad
  • It creates undefined behavior that may pass tests and fail under timing changes.
  • It makes ownership impossible to reason about from the function signature.
  • It turns harmless refactors, such as moving a local variable, into concurrency bugs.
Better habit

Async producers and returned consumers should share explicit state, usually through a small shared object. Capture data by value when a task outlives the stack frame that started it.

Steer clear when a lambda with std::async, std::thread, or callbacks captures locals by &.
Where in this project

src/core/agent.cpp:106 and src/core/agent.cpp:182 start async agent work. Before the fix, these paths captured the returned EventStream by reference. src/core/agent_loop.cpp:416 and src/core/agent_loop.cpp:562 are the loop-side async launches, which now capture the loop context and stream by value.

Avoid 
EventStream stream(...);

std::async(std::launch::async, [&stream]() {
  stream.push(AgentStartEvent{});
});

return stream;
Prefer 
EventStream stream(...); // shares internal state

std::async(std::launch::async, [stream]() mutable {
  stream.push(AgentStartEvent{});
});

return stream;

Antipattern 2

Completion semantics that callers have to remember manually

EventStream::push() accepted final events but did not finish the stream. Only push_and_check() honored the done predicate. That split made it easy to publish an AgentEndEvent and leave readers blocked forever.

Why it is an antipattern

The API exposes two ways to do nearly the same thing, but only one is safe. That forces every caller to carry internal knowledge of the stream implementation.

What changed

Final events now complete the stream through the normal publish path. A reader consuming the returned stream can terminate naturally.

Good APIs make the correct path the boring path.
Where in this project

src/core/stream.h:44 is the normal push() path. This is where final events now honor the stream's done predicate. The risk showed up in callers such as src/core/agent_loop.cpp:419, where every event is published through one helper.

Avoid 
stream.push(AgentEndEvent(messages));

// Reader may block forever because push()
// did not close the stream.
Prefer 
bool push(Event event) {
  if (done_(event)) {
    result_ = extract_(event);
    is_complete_ = true;
  }
  queue_.push(std::move(event));
  condition_.notify_all();
}

Antipattern 3

Multiple test programs linked into one executable

CMake put several test_*.cpp files into a single test-core binary even though each file defined its own main() and duplicated test harness globals.

Why it is bad

It cannot scale. As soon as those translation units are built together, the linker sees duplicate entry points and duplicate symbols.

Why to avoid it

Broken test topology hides actual product defects behind build-system noise. You want each test failure to point at behavior, not target layout.

If test files have their own main(), give each one its own target or centralize the harness.
Where in this project

CMakeLists.txt:39 now creates separate test executables for test_core.cpp, test_agent_loop.cpp, test_agent.cpp, and test_stream.cpp. Before that, those files were grouped into one target even though each had its own main().

Avoid 
add_executable(test-core
  test/test_core.cpp       # has main()
  test/test_agent.cpp      # has main()
  test/test_stream.cpp     # has main()
)
Prefer 
foreach(test_name IN ITEMS core agent stream)
  add_executable(test-${test_name}
    test/test_${test_name}.cpp)
  add_test(NAME test-${test_name}
    COMMAND test-${test_name})
endforeach()

Antipattern 4

Optional code paths that are disabled by default and never checked

The HTTP client was behind PI_CPP_ENABLE_HTTP. Because that option was off, HTTP-only compile errors and dependency gaps could sit unnoticed.

Failure mode
  • The default build stays green while optional users get a broken build.
  • Missing dependencies are discovered late.
  • Code ownership gets fuzzy because few contributors exercise that path.
Better habit

Every supported feature flag should be covered by at least one CI/configure job. Optional code is still production code.

Where in this project

CMakeLists.txt:53 gates the HTTP target behind PI_CPP_ENABLE_HTTP. The HTTP code itself lives in src/http/http_client.cpp. Since that path is off by default, its missing dependencies and compile issues were hidden from the normal build.

Avoid 
option(PI_CPP_ENABLE_HTTP "HTTP" OFF)

if(PI_CPP_ENABLE_HTTP)
  add_library(pi-http src/http/http_client.cpp)
endif()

# CI only builds the default OFF path.
Prefer 
# CI job 1
cmake -S . -B build
cmake --build build

# CI job 2
cmake -S . -B build-http -DPI_CPP_ENABLE_HTTP=ON
cmake --build build-http

Antipattern 5

Returning references out of locked state

AgentState locked a mutex, returned references like const Model&, then released the lock. The caller held a reference to mutable shared data with no protection.

Why it is dangerous

The code looks thread-safe because there is a mutex, but the safety ends before the caller uses the reference.

What to prefer

Return value snapshots for small state, or expose scoped access patterns that keep the lock alive for the whole operation.

A lock that ends before the data is used is often just thread-safety theater.
Where in this project

src/core/agent_state.h:31, src/core/agent_state.h:41, and src/core/agent_state.h:85 are state accessors. These now return snapshots by value. Before the fix, similar accessors returned references after releasing the mutex.

Avoid 
const Model& model() const {
  std::lock_guard lock(mutex_);
  return model_;
}

// lock is gone, reference remains
Prefer 
Model model() const {
  std::lock_guard lock(mutex_);
  return model_; // snapshot
}

// caller owns a safe copy

Antipattern 6

Custom structured data types with implicit invalid states

The hand-rolled JSON value could hold object fields or array items while still being marked as null. Serialization then produced null for populated values.

Why it is an antipattern

The representation allowed contradictory state: data existed, but the tag said it did not. That is the kind of bug type systems are supposed to prevent.

How to steer clear

Use a proven JSON library when possible. If a custom type is necessary, make constructors and mutators preserve invariants automatically.

Where in this project

src/core/message_types.cpp:114 defines the custom JsonValue. The issue was in object and array construction: populated values could still have JsonKind::null_t. The invariant is now enforced in mutators like operator[] at src/core/message_types.cpp:153 and set() at src/core/message_types.cpp:170.

Avoid 
JsonValue j;          // kind == null_t
j.obj.emplace_back("id", "gpt-4");

serialize(j);        // returns "null"
Prefer 
JsonValue& set(key, value) {
  kind = JsonKind::object_t;
  obj.emplace_back(key, value);
  return obj.back().second;
}

serialize(j);        // returns an object

Antipattern 7

Manual resource cleanup scattered through HTTP code

The libcurl code manually initialized handles, built header lists, performed requests, cleaned up, and queried status. That created cleanup-order bugs and malformed auth headers.

Why it is bad
  • Cleanup after early returns is easy to miss.
  • Using a handle after cleanup is undefined behavior.
  • Small protocol mistakes, such as missing Authorization:, are hard to spot in low-level setup code.
Better habit

Wrap resources in RAII objects so lifetime follows scope. Build headers with helpers that encode protocol details once.

In C++, manual cleanup is usually a smell when RAII can express the lifetime.
Where in this project

src/http/http_client.cpp:16 and src/http/http_client.cpp:28 now wrap curl handles and header lists. The risky code was in HttpClient::post() and post_streaming(), now centered around src/http/http_client.cpp:168 and src/http/http_client.cpp:219.

Avoid 
CURL* curl = curl_easy_init();
curl_slist* headers = nullptr;

curl_easy_perform(curl);
curl_slist_free_all(headers);
curl_easy_cleanup(curl);
curl_easy_getinfo(curl, CURLINFO_RESPONSE_CODE, &status);
Prefer 
struct CurlHandle {
  CURL* handle{curl_easy_init()};
  ~CurlHandle() { curl_easy_cleanup(handle); }
};

CurlHandle curl;
curl_easy_perform(curl.handle);
curl_easy_getinfo(curl.handle, CURLINFO_RESPONSE_CODE, &status);

Antipattern 8

Callbacks whose results are computed and ignored

The tool loop called after_tool_call, unpacked the override tuple, and then did not apply it. That makes extension points misleading.

Why it is harmful

Users believe they can modify tool output, but the system silently discards the requested override.

What to do instead

Either implement the callback contract fully or remove the hook until the behavior exists. Half-contracts are worse than no contract.

Where in this project

src/core/agent_loop.cpp:253 and src/core/agent_loop.cpp:333 call after_tool_call. Before the fix, the override tuple was unpacked and then ignored. It now replaces the tool result with a concrete StaticToolResult.

Avoid 
auto override = after_tool_call(...);
if (override) {
  auto [content, is_err, terminate] = *override;
  // values are never used
}
Prefer 
auto override = after_tool_call(...);
if (override) {
  auto [content, is_err, terminate] = *override;
  tool_result = std::make_shared<StaticToolResult>(
    std::move(content), is_err, terminate);
}

Practical guardrails

Rules worth keeping in this codebase

Ownership

If work crosses a thread boundary, capture by value or share explicit state. Avoid default reference captures in async code.

APIs

Do not create two similar methods where one silently skips required behavior. The ordinary method should be safe.

Builds

Every executable should have exactly one entry point. Every supported feature flag should be configured somewhere.

State

Thread-safe classes should not return unlocked references to mutable internals. Return snapshots or scoped access.

Default verification after fixes: cmake --build build and ctest --test-dir build --output-on-failure --timeout 10.
